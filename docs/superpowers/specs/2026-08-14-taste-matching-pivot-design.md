> *"The app **primarily features** astrology, horoscopes, palm reading, fortune telling or zodiac reports…"*

4.3(b) 는 컨셉 판정이라 논증으로 뒤집기가 사실상 불가능하다. **논증하지 않고 저 문장을 거짓으로 만든다** — 관상을 매칭 축 6개 중 하나로 격하하고, 주 루프를 취향 문제 매칭으로 옮긴다. 심사관이 앱에서 직접 확인 가능한 형태여야 한다.

### 0.3 부차적 진단 — 심사관은 이 앱을 완주할 수 없었다

케미 그룹은 정원 6·8·10·12인이 차야 결과가 나온다. 심사관은 혼자다. 홈이 케미 로비여도 **심사관 기기에서 실제로 재생된 것은 셀피 → 관상 리포트 하나뿐**이었다. §7 이 이 문제를 다룬다.

### 0.4 확정된 전략

- **제품**: 취향 문제 매칭이 주축. 얼굴 계측 호환성은 방장이 켜는 선택 축.
- **포지션**: 이미 아는 사람 / 같은 자리에 있던 사람의 관계망 확장. 공개 그룹 목록은 **유지**한다 (모임 브라우징이지 사람 브라우징이 아니다 — §3).
- **레코드**: `com.scienceintegration.facely` **유지**. MeSo 이관은 롤백 (§8).
- **버전**: `2.0.0` 신규 버전으로 제출 → 새 Submission ID → 진짜 새 심사.
- **제외**: 정치 성향 축. 개인정보보호법 §23 상 민감정보라 별도 동의 없이 처리 불가. 심사가 아니라 법 문제라 협상 대상이 아니다.

### 0.5 손대지 않는 것

케미 그룹의 상태 머신(방 생성 · QR/링크 셀프 조인 · 정원 충족 자동 시작 · revealing · 48h 만료 · 30일 purge), 매칭 성사·상호동의 채팅, 신고·차단(`team_reports` · `user_blocks`), 코인 경제, 온디바이스 468 landmark 계측 파이프라인. **전부 그대로 간다.**

### 1.1 축 목록

| id | 표시 이름 | 문항 | 입력 |

| `face_compat` | **얼굴 호환** | — | 측정값 (기존 궁합 엔진) |

**전부 객관식이다.** 자유 입력이 없으면 Guideline 1.2 의 UGC 필터링 요건이 문항에 적용되지 않는다. (채팅·방 제목은 기존대로 신고·차단으로 커버.)

`taste_food` 는 민초/반민초, 부먹/찍먹 류 밸런스 게임 소재를 쓴다. 갈등 없이 대화가 터지는 축이라 첫 방 기본 추천으로 적합하다.

### 1.2 `face_compat` 의 위치

- 방 만들기 화면 **축 목록의 맨 아래**, 기본 **off**
- 한 번도 켜지 않고 앱 전체가 완전히 작동한다 ← 심사 노트의 검증 가능한 주장(§6.3)
- 숨기는 것이 아니라 **실제 선택 항목**이다. 심사용 은닉은 2.3.1 위반이라 하지 않는다.

### 1.3 축별 스코어링

정답/오답 이분법은 6문항에서 점수가 0·17·33·50… 으로 계단이 심하다. **문항마다 선택지 유사도 행렬**을 둔다.

```
문항 q 의 선택지 집합 O_q, 대칭 유사도 행렬 S_q (대각 1.0, 범위 [0,1])
두 사람 a·b 의 문항 점수     = S_q[answer_a][answer_b]
축 점수 (0~100)              = mean_q( S_q[a][b] ) × 100
```

행렬은 데이터(상수 테이블)라 코드 복잡도가 아니라 콘텐츠 작업이다. 예 — `액션`↔`SF` 0.6, `액션`↔`로맨스` 0.2.

`face_compat` 축 점수는 **기존 `CompatPipeline` 총점(0~100)을 그대로 쓴다. 궁합 엔진 무변경.**

## 2. 방 생성 흐름

### 2.1 축 선택

방장이 방을 만들 때 **1~3개 축**을 고른다. 기본값은 취향 축 1개(추천). 고른 축이 방 속성으로 고정되고, 참가자는 조인 시 그 축의 문항에만 답한다.

### 2.2 방 유형

`all` / `match` 2종 **유지**. `all` 이 기본이고 `match`(남녀 반반)는 방 만들 때 고르는 유형 하나로 남긴다. 한국 시장 수요가 실재하므로 기능은 유지하되 기본 노출은 아니다.

### 2.3 참가자 흐름

```
조인 → (없으면) 얼굴 카드 만들기 → 방 축의 문항 답하기 → 슬롯 점유
                                                    ↓
                              정원 충족 → 자동 시작 → 결과 공개
```

문항 답변이 슬롯 점유의 전제가 된다. 기존 `team_members` 에 답변 컬럼이 추가된다.

## 3. 공개 그룹 목록

**유지한다.** 콜드 스타트와 서클 확장의 핵심 진입면이고, 이게 없으면 방장이 이미 6~12명을 모을 수 있는 순간에만 앱이 작동한다.

dating 판정의 축은 "낯선 사람이 만나는가"가 아니라 **"무엇을 브라우징하는가"** 다. Meetup·밴드·소모임·당근 전부 낯선 사람을 연결하고 승인돼 있다. 이 목록은 **방**을 브라우징한다.

### 3.1 카드 구성

| 넣는다 | 넣지 않는다 |
| --- | --- |
| 방 제목 · 축 태그 (#영화 #음악) | 참가자 얼굴 격자 |
| 인원 `4/8` · 마감까지 남은 시간 | 개인 프로필 직행 링크 |
| 방장 닉네임 (사진 아님) | "근처 N명" · 거리 |
| 방 유형 · 공개/비밀 | 성별·나이를 **탐색 필터**로 노출 |

**방을 고르는 화면이지 사람을 고르는 화면이 아니다.** 방에 들어간 뒤의 참가자 목록·사진 공개·매칭 결과는 기존 그대로 두어도 무방하다 — 같이 게임하는 사람들의 맥락 안이다.

기존 `team_title_catalog.dart` 의 6 카테고리(지역/직업/MBTI/취미/즉석/기타)는 축 태그와 함께 그대로 쓴다.

## 4. 매칭 계산 — `compat_aggregator` 다축 확장

### 4.1 현행

```
rawTotal  = 0.20·element + 0.40·palace + 0.25·qi + 0.15·intimacy
spread    = clamp(50 + (rawTotal-50)·1.4, 5, 99)
total     = _remapToUserScale(spread)     // p30/p60/p90 → 56/78/90
```

### 4.2 변경

축이 방마다 다르므로 고정 가중치를 쓸 수 없다.

```
axisScores = { 방이 켠 축들 → 각 0~100 }
rawTotal   = mean(axisScores)             // 동일 가중
spread     → _remapToUserScale            // 기존 파이프라인 재사용
```

**라벨 경계(56/78/90)와 4단 라벨은 그대로 둔다.** 사용자가 보는 점수 체계가 축 구성에 따라 흔들리면 안 된다.

### 4.3 ⚠️ 검증이 필요한 지점

`_remapToUserScale` 의 anchor 는 궁합 엔진 raw 분포(20k-pair MC, p30/p60/p90 = 50.54/54.44/59.63)에 맞춰 튜닝돼 있다. **취향 축의 raw 분포는 이와 다르다.** 축별로 MC 를 돌려 공통 스케일로 정규화한 뒤 집계해야 한다. 안 하면 취향 축만 켠 방에서 점수가 한쪽으로 쏠린다.

구현 계획에서 축별 분포 측정 → 정규화 상수 도출을 독립 태스크로 잡는다.

## 7. 심사관 완주 경로

혼자인 심사관이 `조인 → 답변 → 정원 충족 → 결과 공개 → 매칭 → 채팅` 전체를 재생할 수 있어야 한다. 이것이 없으면 build 15 가 반복된다.

**`web/db/tests/demo_teams.sql` 을 재활용한다.** 이미 6개 방(모집중·revealing·expired)을 시드하고 베스트 케미 쌍까지 실측 검증해둔 스크립트가 있다.

추가 설계:

- 심사용 계정 하나로 로그인하면 **5/6 이 찬 공개 방**이 보인다
- 심사관이 6번째로 조인 → 문항 답변 → **즉시 정원 충족 → 자동 시작 → 결과 공개**
- 베스트 쌍에 심사관이 포함되도록 시드 → 매칭 카드 → 수락 → 채팅방 진입까지 재생
- 시드 계정 5개의 답변·metrics 를 미리 채워둔다
